# Node storage and retrieval model

## Overview

OmniDocQA uses a document section tree, not an entity-relationship
knowledge graph. A document is split into leaf chunks and section nodes are
created from the chunks' `section_path` values.

```text
Part I (section, level=1)
└── Item 1 (section, level=2)
    └── Business (section, level=3)
        ├── chunk-1 (chunk, level=0)
        └── chunk-2 (chunk, level=0)
```

`level=0` identifies a leaf chunk. `parent_id` identifies its immediate
parent; it does not contain all ancestors. Section and chunk IDs are UUIDs
generated by the application.

## ID and relationship mapping

| Application field | PostgreSQL | Qdrant | Meaning |
|---|---|---|---|
| `node_id` | `rag_nodes.id` | Point `id` and payload | Unique node identity |
| `parent_id` | `rag_nodes.parent_id` foreign key | Payload field | Immediate parent node ID |
| `document_id` | `rag_nodes.document_id` → `rag_documents.id` | Payload field | Document grouping/filter |
| `ingest_run_id` | `rag_nodes.ingest_run_id` → `rag_ingest_runs.id` | Payload field | Ingestion run |
| `level` | Column | Payload field | Tree depth; `0` means leaf |

PostgreSQL defines the self-reference as:

```sql
parent_id UUID REFERENCES rag_nodes(id) ON DELETE CASCADE
```

This constraint exists only in PostgreSQL. Qdrant stores `parent_id` as
payload and does not enforce foreign keys or recursive cascades.

## Two storage roles

PostgreSQL is the canonical node store. It keeps the complete text, metadata,
the relational tree, and the generated `search_vector` used by the PostgreSQL
sparse backend. It supports sibling queries and recursive leaf-descendant
queries.

Qdrant is the dense vector index. Each node's `text` produces one embedding;
the node ID, document ID, parent ID, level, title, and metadata are stored as
payload for filtering and result identification. These fields are not part of
the embedding vector. A short `text_preview` is stored in the current Qdrant
payload, while the complete text remains in PostgreSQL.

The ingestion path is:

```text
NodeRecord
  ├── PostgreSQL rag_nodes (full record)
  ├── text → embedding → Qdrant vector
  └── IDs/metadata → Qdrant payload and sparse index fields
```

The dense and sparse results are fused by the retrieval layer. OpenSearch is
an optional sparse backend; when it is not selected, PostgreSQL full-text
search is used.

## Level-0 retrieval and tree expansion

Leaf retrieval passes `levels=[0]` to both dense and sparse backends:

```text
Qdrant: payload filter level == 0 + vector similarity
PostgreSQL: WHERE level = ANY([0]) + search_vector ranking
```

After a section hit, PostgreSQL can recursively traverse `parent_id` to find
all level-0 descendants. After a leaf hit, it can select other level-0 rows
with the same `parent_id` as bounded sibling context.

Qdrant could also filter sibling payloads by `parent_id`, but that would be a
payload/scroll operation rather than a relational query and would not provide
PostgreSQL's complete text, foreign-key guarantees, or recursive CTE support.

## Replace versus vector reindex

`replace_document_nodes()` in the Qdrant backend deletes all points whose
payload has the target `document_id`, then upserts the supplied points. It
does not delete by recursively following `parent_id`.

- Normal re-ingestion builds new `NodeRecord` objects with new UUIDs, replaces
  the PostgreSQL rows, and writes those new IDs to Qdrant.
- `reindex-vectors` reads existing PostgreSQL nodes, keeps their `node_id` and
  `parent_id`, regenerates embeddings, and writes points with the same IDs.

Qdrant and PostgreSQL do not share one transaction, so the ingestion code
avoids clearing existing Qdrant vectors when PostgreSQL has nodes but no
embeddings were produced.
