# 企业级 RAG 设计借鉴规则

> 目的：为后续 FinanceRAG 的重构、功能扩展和技术选型提供统一判断标准。
>
> 适用范围：数据导入、文档建模、检索、上下文组装、答案生成、评估和生产运维。

## 使用方式

每次重构前先回答三个问题：

1. 这项改动解决了哪一个可观测的业务问题？
2. 它会影响哪些数据结构、检索阶段或证据链？
3. 如何用离线数据集、线上指标或回归测试证明改动有效？

规则等级：

- **MUST**：违反后会导致数据不可追溯、结果不可验证或生产风险明显增加。
- **SHOULD**：默认遵守，只有明确的性能、成本或兼容性原因才例外。
- **MAY**：按业务场景选择，不作为所有场景的强制要求。

## 一、业务目标规则

### R1：先定义信息损耗，再定义 RAG 功能（MUST）

不要以“接入大模型”或“增加一个检索器”作为目标。每项能力必须对应一个业务问题，例如：

- 减少查找财报和监管信息的时间；
- 缩短尽调或监管响应周期；
- 降低人工核对财务指标的成本；
- 提高答案的可追溯性和审计效率。

### R2：用业务指标验证技术改动（MUST）

重构前后至少比较一类指标：

- 检索：Recall、Context Precision、Evidence Coverage；
- 生成：Faithfulness、Citation Accuracy、Answerability；
- 工程：P50/P95 延迟、失败率、单次调用成本；
- 业务：人工查找时间、审核周期、有效答案比例。

不能只凭少量人工体验判断系统变好了。

### R3：区分“回答不了”和“回答错误”（MUST）

系统应允许明确返回证据不足、文档缺失或问题超出范围，而不是在证据不足时强行生成结论。答案接口应保留 limitations、confidence 和来源信息。

## 二、文档与数据建模规则

### R4：元数据先于向量（MUST）

每个可检索节点必须有稳定、可过滤、可追溯的元数据。至少包括：

- `document_id`、文件来源和文档类型；
- `section_path`、章节标题和章节角色；
- 节点层级、父节点和文档内顺序；
- `form`、`filed`、`accn`、`cik` 等金融事实关联字段；
- 数据版本、解析器版本和 Embedding 模型版本。

向量相似度不能替代文档范围、时间范围和财务口径过滤。

### R5：保留文档天然结构（MUST）

优先根据 HTML、PDF 或原始文件的标题、表格、段落和引用关系构建 section tree，不要一开始就把全文切成互相独立的固定长度文本。

### R6：采用分层节点，而不是单一 chunk（SHOULD）

建议至少保留以下层级：

| 层级 | 作用 |
| --- | --- |
| 文档层 | 确定来源、公司、期间和文档类型 |
| 章节层 | 定位主题和上下文范围 |
| 段落层 | 作为主要召回和生成证据 |
| 句子层 | 作为精确引用和事实核验单元 |

不同层级可以使用不同的索引和召回策略，但不能丢失父子关系。

### R7：每个节点都必须能回到原文（MUST）

节点应能定位到原始文档、章节、顺序和必要的字符/页码范围。任何生成给用户的引用都必须可以通过 node ID 或文档定位信息复核。

### R8：数据版本必须可重建（MUST）

导入记录需要保存解析器、切分策略、Embedding 模型、向量维度和索引后端等版本信息。修改这些内容后，必须能够判断哪些文档需要重新导入或重新索引。

## 三、解析与切分规则

### R9：按数据格式选择解析链路（MUST）

PDF、HTML、Word、扫描件、CSV 和图表不能默认使用同一个解析器。解析流程应明确区分：

- 纯文本提取；
- OCR；
- 表格结构提取；
- 图表视觉理解；
- 财务事实结构化抽取。

### R10：切分目标是证据完整，而不是长度均匀（MUST）

切分时优先保证一个节点表达完整的事实、条件、期间和结论。长度只是约束，不是唯一目标。需要通过 overlap、父节点扩展或 sibling expansion 保留上下文。

### R11：为不同任务保留不同粒度（SHOULD）

叙述性问题适合章节/段落级上下文，数值核验适合财务事实行和句子级证据。不要用同一个 chunk 规则覆盖所有问答类型。

## 四、检索规则

### R12：拒绝纯向量检索（MUST）

企业金融场景默认采用混合检索：

```text
元数据/规则过滤
        + dense semantic retrieval
        + sparse keyword retrieval
        + SQL financial facts
        + reranking
        = final evidence set
```

向量检索适合召回语义相近内容，但不擅长精确处理 accession、指标名、表单类型、日期和数值口径。

### R13：先缩小范围，再扩大上下文（SHOULD）

推荐顺序：

1. 根据文档、公司、表单、期间等元数据确定范围；
2. 执行 dense 和 sparse 粗召回；
3. 使用 SQL 事实或章节关系补充证据；
4. 对 top seeds 扩展父子节点和相邻节点；
5. 在最终上下文预算内排序、去重和截断。

### R14：检索结果必须可解释（MUST）

检索结果至少保留：查询、后端、阶段、分数、过滤条件、node ID 和最终入选原因。调试信息可以按开关返回，但不能让线上结果失去追踪能力。

### R15：重排序是精排，不是数据修复（MUST）

Reranker 只能在候选集合中重新排序，不能弥补错误的解析、缺失的元数据或过窄的初始过滤。必须先保证候选池覆盖，再使用 rerank 提升顺序。

### R16：检索必须具备回退策略（MUST）

OpenSearch 不可用、稀疏检索无结果、SQL 无匹配或某个模型调用失败时，应有明确的降级路径，并在 pipeline trace 中记录降级原因。

### R17：复杂关系使用图检索增强（MAY → SHOULD）

当文档存在大量交叉引用、法规关联或跨文档证据依赖时，引入引用图或实体关系图。图检索应作为召回增强层，不应替代基础的文档过滤和向量/稀疏检索。

## 五、上下文与答案规则

### R18：上下文预算必须显式控制（MUST）

上下文组装必须有字符或 token 预算，并记录截断、去重和被淘汰的证据。不能仅依赖固定 `top_k` 代表上下文质量。

### R19：证据优先于流畅表达（MUST）

答案生成只能基于已检索证据。无法从证据确认的内容应明确标注不确定性，不得为了完整回答而补写来源中不存在的事实。

### R20：引用和结论分离（MUST）

系统内部应区分：

- 最终结论；
- 支撑结论的证据节点；
- 财务事实 SQL 行；
- 证据原文摘录；
- 局限性和置信度。

这样可以分别评估回答是否正确、引用是否准确以及证据是否充分。

### R21：SQL 事实和叙述性 RAG 互相校验（SHOULD）

涉及收入、利润、现金、债务、期间变化等问题时，优先使用 SQL 事实确认数值，再使用财报段落解释原因、背景和管理层表述。两者冲突时，应显式报告冲突，而不是静默选择一个结果。

## 六、模型与成本规则

### R22：模型选择必须同时评估质量、成本和合规（MUST）

评估维度包括：

- 专业术语和数值理解；
- 幻觉和拒答表现；
- 单次调用成本；
- 数据是否允许出网；
- 是否支持私有化部署和微调；
- 延迟、吞吐和服务稳定性。

### R23：优先优化检索，再考虑更大模型（SHOULD）

许多“模型回答不好”的问题实际来自召回范围、元数据、切分和上下文组装。模型升级前应先确认输入证据是否正确、完整和可解释。

### R24：对高频领域任务进行专门适配（SHOULD）

针对 SEC 财报，应优先建设财务指标词典、表单类型、期间表达、会计口径和公司/行业术语映射，再决定是否进行模型微调。

## 七、生产工程规则

### R25：每个阶段都要可观测（MUST）

至少记录：路由结果、SQL 查询摘要、dense/sparse 命中数、候选数、rerank 状态、上下文字符数、LLM 延迟、错误类型和 trace ID。日志中不得记录密钥或不必要的敏感正文。

### R26：关键依赖必须有健康检查和降级（MUST）

PostgreSQL、Qdrant、OpenSearch、LLM、Embedding 和 reranker 都应有启动检查、超时、重试边界和降级行为。

### R27：索引和数据库变更必须可回滚（MUST）

Schema、向量维度、索引名称和检索字段变更前，应保留迁移方案、旧索引或重建路径。禁止在没有备份和验证的情况下直接删除旧数据。

### R28：安全和合规是功能的一部分（MUST）

生产部署至少需要考虑 API 鉴权、租户隔离、敏感字段脱敏、密钥管理、访问审计、限流和数据保留策略。

## 八、当前项目重构对照表

| 规则方向 | 当前已有能力 | 后续优先级 |
| --- | --- | --- |
| 节点化结构 | section tree、父子节点、叶子 chunk | 保留并补充版本字段 |
| 混合检索 | Qdrant + PostgreSQL/OpenSearch | 统一接口和回退策略 |
| 金融事实 | SEC observations SQL 查询 | 增强指标、期间和 RAG 证据对齐 |
| 上下文组装 | sibling expansion、字符预算、去重 | 增加证据覆盖率指标 |
| 重排序 | Bocha、narrative multi-rerank | 明确候选池和失败降级 |
| 证据链 | pipeline trace、evidence UI | 强化原文定位和引用校验 |
| 图检索 | 当前主要是 section tree | 增加跨文档引用关系后再引入 |
| 句子检索 | 当前以段落节点为主 | 在引用精度不足时建设 |
| 多模态 | 非纯文本支持有限 | 按业务需求建设表格/OCR链路 |
| 评估 | RAGAS + Langfuse | 建立固定回归数据集和门禁 |

## 九、重构完成检查清单

- [ ] 是否明确了重构要改善的业务指标？
- [ ] 是否保留了文档、章节、节点和原文定位关系？
- [ ] 是否同时考虑了元数据、dense、sparse、SQL 和 rerank？
- [ ] 是否记录了每个检索阶段的输入、输出和过滤原因？
- [ ] 是否有无结果、依赖不可用和低置信度的回退策略？
- [ ] 是否能验证答案中的每个关键数字和结论？
- [ ] 是否补充了离线回归问题和自动评估指标？
- [ ] 是否评估了延迟、成本、数据安全和可部署性？
- [ ] 是否有索引/Schema 迁移、备份和回滚方案？
- [ ] 是否更新了 README、环境变量示例和运行文档？

## 核心原则

> 企业级 RAG 不是“LLM + 向量数据库”，而是一套以业务问题为起点、以结构化元数据为基础、以混合检索和证据链为核心、以可观测性和业务指标为验收标准的信息系统。
